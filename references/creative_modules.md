# 创意模块算法说明

> 本文件解释 `scripts/party_plus.py` 中每个创意模块的**评分依据与阈值**。
> 设计原则：**能算的绝不猜**——所有输出均可复现、可解释、可被用户核对。

## ① 成团概率雷达 `formation_radar`

| 维度 | 条件 | 分值 |
|---|---|---|
| 成团线 | 已达到 `partyMin` | 基础 68 |
| | 每差 1 人 | −11 |
| 余位 | `leftNum ≥ 人数+3` | +8 |
| | `leftNum ≥ 人数` | +2 |
| | 不足 | −22 |
| 筹备窗口 | 距活动 ≤2 天 | −16 |
| | 3–7 天（拉人黄金期） | +10 |
| | 8–14 天 | +5 |
| | >14 天 | −3 |
| 周末（含法定周日历未接） | 周六/周日 | +7 |
| 时段 | 晚市（≥17:00） | +4 |

结果夹在 **5%–95%** 之间（不承诺 100%，因为成团最终取决于他人报名）。

等级：≥80 高 / 60–79 较高 / 40–59 一般 / <40 偏低。

## ② 包场 vs 拼团 `compare_modes`

```
包场总价 = 人均价 × max(需求人数, partyMin)     # 场地保底
拼团总价 = 人均价 × 需求人数                      # 需 > partyMin 才可发起
```

推荐规则：
- 拼团不可发起（人数 ≤ 起订线）→ 只能包场
- 拼团更贵 → 推荐包场
- **两者同价 → 推荐包场**（同样的钱换取"确定举办"，规避未成团退款风险）

> 实测数据：SPU 1779 两种模式人均均为 ¥50，因此真正的差别是**确定性**，这正是本模块的价值——把"看不见的风险"摆到台面上。

## ③ 派对黄历 `party_almanac`

```
基准分 50
有官方营销活动      +18
周末                +12
余位充足            +10
满足提前 3 天预订    +8（不满足则 −30）
距今天数 3–14 天     +5
```

判定：≥70 **宜** / 55–69 **可** / <55 **忌**。

数据源 `campaign-calendar` 返回的 markdown 文本，用正则提取 `#### YYYY年M月D日` 与 `**活动标题**：`。

## ④ 儿童营养安心指数 `kids_nutrition_audit`

参考区间（4–12 岁儿童**单餐**，非官方结论）：

| 指标 | 上限 |
|---|---|
| 热量 | 700 kcal |
| 钠 | 800 mg |
| 脂肪 | 26 g |

按**超出比例**扣分（避免"只超一点就重罚"）：

```
热量超出 x% → −x × 1.5    （最多 −30）
钠   超出 x% → −x × 3.0    （最多 −35）
脂肪 超出 x% → −x × 2.0    （最多 −20）
```

评级：≥85 A / 70–84 B / <70 C。

替换建议来自 `SWAPS` 高负担→低负担映射（如 中薯条→小薯条、可乐中杯→无糖可乐），按 `Δ钠×2 + Δ热量` 排序取前 3 条，并**如实显示增/减**（例：换无糖可乐会减 147 kcal 但增 35mg 钠）。

实测样例：吉士汉堡包 + 中薯条 + 可乐中杯 = 730 kcal / 钠 838mg → **79 分 B**。

## ⑤ 筹备时间线 `party_timeline`

| 节点 | 待办 |
|---|---|
| T-7 | 确定人数与预算，初选门店/时段 |
| T-5 | 发起拼团招募（如走拼团） |
| T-3 | ⚠️ **预订截止**（官方要求提前 3 天） |
| T-1 | 最终确认人数；如需餐食提前点餐 |
| T | 提前 15 分钟到店 |

当 `预订截止 − 今天 ≤ 3 天` 时输出强提醒。

## ⑥ 招募卡 / 邀请函

- 招募卡：余位进度条 `█░`、报名 x/y、成团概率、还差几人——全部来自实时接口。
- 邀请函：单文件 HTML，麦当劳红 `#DA291C` + 黄 `#FFC72C`，浅色卡片，含报名进度条与"成团概率"徽章。

## ⑦ 四宫格比选 `scout_grid`

| 格 | 取值方式 |
|---|---|
| 最优综合 | 五维调度评分第一名 |
| 最省人均 | `price` 最小 |
| 最近门店 | `distance` 最小 |
| 空位最多 | `leftNum` 最大 |
